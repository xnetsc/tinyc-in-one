Linux host 9/9). Three local commits, one per host; no version bump;
no push. The rule being implemented: every host's package carries all
9 targets (linux x86_64 / aarch64 / riscv64, win32 x86_64, android

## Windows host (`038a478`)

`build.sh` gains `build_host_mingw_for <triple> <cross-name>
<target-def> <isa> [extra -D flags...]` and the `./build.sh host-win
[target-triple...]` dispatch. One PE dual-form compiler per target,
all with host `x86_64-w64-mingw32`. The native `x86_64-w64-mingw32`
keeps the proven `build_host_mingw` recipe; the other 8 use the same

with the same internal layout as `build/dist/<triple>/`, plus `bin/`
companions so the `.exe` works when run directly.

### PE export-list fix (in the new function only)

The cross PE link failed at first for wasm32: the `.def` export list
(generated by `tools/gen_windows_def.py` from `libtcc.h`) listed
symbols the cross compiler does not define: `tcc_relocate`,
`_tcc_setjmp`, `tcc_set_backtrace_func` (wasm32) and additionally
`tcc_run` (the other cross targets; wasm32 has a `tcc_run` stub in
`wasm-backend/src/wasm-link.c`). The three symbols live only in
`tccrun.c`, whose whole body is inside `#ifdef TCC_IS_NATIVE`, and
`TCC_IS_NATIVE` is defined only when host CPU matches target CPU —
plus the PE condition `defined _WIN32 == defined TCC_TARGET_PE`
fails for cross targets, since they do not pass `-DTCC_TARGET_PE`.
So all 8 cross PEs lack `-run` support, exactly like the ELF cross
dists (verified: the Linux `aarch64-linux-gnu` ELF dist also lacks
`tcc_run` / `tcc_relocate` / `_tcc_setjmp`). The fix, local to the new
function (`gen_windows_def.py` and the native recipe untouched):
compile the unity sources to `.o` first, filter the `.def` to symbols
`nm --defined-only` reports as defined, then link the `.o` files.
The native win32 PE needed no filtering (all 41 exports defined).

### Link-time condition (same on every host)

Linking a hosted executable for a linux-gnu target needs the target's
runtime `libc.so.6` findable through the baked lib paths — on Linux
that is the cross sysroot's lib directory, which Windows does not
have. So on the Windows host the three linux-gnu targets compile to
object and link freestanding programs; the other six link fully
(darwin via bundled `.tbd`, android via bundled bionic stubs, wasm32
needs no libc, win32 via `msvcrt.dll`).

### `native-libs` (build.sh)

- Kernel tree prep: wasm-backend sources (`wasm-backend/src/wasm-gen.c`,
  `wasm-link.c`, `wasm-int.h`) + `wasm-backend/patches/apply-patches.py`
  (same order as top-level `build_wasm32`), and the `config.h` guard
  edit (adds `|| TCC_TARGET_WASM32` to the `TCC_TARGET_C67` guard)
  done with python3 instead of `sed -i` for portability. Native
  make, then cross makes for `x86_64 arm64 riscv64 x86_64-win32
  arm64-osx x86_64-osx` (vendor Makefile `cross-%` rule is generic,
  so `make cross-x86_64` works on any host). Win32 pthread merge
  after `cross-x86_64-win32` (same as top-level `add_win32_pthread`:
  compile `win32/lib/pthread.c` with `$SRC/x86_64-win32-tcc
  -B"$SRC/win32"`, `ar r` into `x86_64-win32-libtcc1.a`).
  `runmain.o` for the two android targets unchanged (native `tcc`
  for x86_64, `arm64-tcc` for aarch64).
- `build_so <abi> <triple> <tdef> <elflib>`: one `.so` per (device
  ABI, compile target), 2 ABIs x 9 targets = 18 files named
  `libtinyc-<triple with '-' as '_>.so`. The NDK compiler is selected
  by DEVICE ABI only (`aarch64-linux-android30-clang` for arm64-v8a,
  `x86_64-linux-android30-clang` for x86_64; fallback strips the API
  suffix) — never by compile target (riscv64 has no NDK clang). TDEF
  per target matches top-level `build.sh`: linux-gnu
  `-DTCC_TARGET_<arch>`; android adds `-DTARGETOS_ANDROID=1` (only
  for the two android targets — it selects the Android ELF
  interpreter/library model, wrong for any other target); darwin adds
  `-DTCC_TARGET_MACHO`; win32 `-DTCC_TARGET_X86_64 -DTCC_TARGET_PE`;
  wasm32 `-DTCC_TARGET_WASM32`. ELF interpreter
  `/system/bin/linker64` baked only for the android targets (other
  targets use TCC's default for their own platform). Baked search
  paths stay the android-style device paths for every target (`{B}`
  = extracted toolchain dir; sysroot comes from Java-registered
  paths). No `CONFIG_TCCDIR` baked (unlike the top-level win32 dist,
  which bakes an absolute build-machine path): `libtcc1.a` sits at the
  standard `<toolchain>/lib/libtcc1.a` for every target, and win32
  headers reach user programs through the Java-registered sysroot.
  Link-time note, same as every other host: the three linux-gnu
  targets compile to object and link freestanding programs on the
  device (no glibc runtime); the other six link fully (darwin via
  bundled `.tbd`, android via device bionic, wasm32 needs no libc,
  win32 via `msvcrt.dll`). Stale `libtinyc*.so` removed before
  building.
- Toolchain assets staging (per target, from the tree + dist):
  `toolchain/<triple>/include/` = builtin headers (`$SRC/include/*.h`
  + `tcclib.h`); `toolchain/<triple>/lib/libtcc1.a` from the
  cross-make output per target (x86_64 -> `x86_64-libtcc1.a`, arm64
  -> `arm64-libtcc1.a`, riscv64 -> `riscv64-libtcc1.a`, win32 ->
  `x86_64-win32-libtcc1.a` pthread-merged, arm64-osx ->
  `arm64-osx-libtcc1.a`, x86_64-osx -> `x86_64-osx-libtcc1.a`;
  android targets share the same-CPU archive as their linux-gnu
  twin; wasm32 has none — its runtime helpers are host-provided
  imports). `runmain.o` only for the two android targets (other seven
  follow the top-level dists, which stage no `runmain.o` for cross
  targets). Darwin `.tbd` stubs from the dist's `lib/tcc/lib/` into
  `toolchain/<triple>/lib/`; win32 tree from the dist's
  `lib/tcc/win32/` into `toolchain/<triple>/win32/`.
- Sysroot staging (per target, from the dist): linux-gnu/android
  `include-libc` -> `include`, `libc` -> `lib`; darwin
  `include-libc` -> `include` (no lib — links the `.tbd` from the
  toolchain lib); win32 `win32/include` -> `include`, `win32/lib` ->
  `lib`; wasm32 `lib/tcc/include` -> `include` (no lib).
- Manifest assertion `assert_dist <triple>`: every target's dist
  must exist and its `manifest.json` `"target"` must equal the
  triple (python3 JSON check); missing/wrong dist fails the build,
  never ships an AAR with a silently empty toolchain or sysroot (the
  lesson of the once-empty AAR sysroot).
- `.gitignore` updated: the old rule ignored only
  `jniLibs/*/libtinyc.so`; now `libtinyc*.so`, plus
  `toolchain/*/lib/*.tbd` and `toolchain/*/win32/**` (the darwin
  stubs and the win32 tree were previously untracked build output).

  order), `isSupportedTarget(String)`, `soNameForTriple(String)`
  (`libtinyc-` + triple with `-` -> `_`, for `loadLibrary`);
  `init(Context, String targetTriple)` overload (validates against
  the allowlist, throws `IllegalArgumentException` otherwise;
  extracts `toolchain/<triple>` + `sysroot/<triple>`; sets the kernel

  `TinycNative.ensureLoaded(triple)`); existing `init(Context)` now
  delegates to `init(context, tripleForCurrentAbi())`.
  `ASSETS_VERSION` `"2"` -> `"3"` (bumped by the build's placeholder
  mechanism; included in this commit).
- `TinycNative.java`: the `boolean loaded` flag replaced by `String
  loadedTarget`; `ensureLoaded(String targetTriple)` loads
  `tinyc-<sanitized>` via `System.loadLibrary`, returns early for the
  same target, throws `IllegalStateException` on a different target
  after the first load (JNI methods resolve by name at first call, so
  the first-loaded `.so` wins — a second target's same-named JNI
  methods would never bind, so switching must fail loudly rather
  than silently use the wrong compiler). No-arg `ensureLoaded()` now
  returns early if anything is already loaded (keeps the loaded
  target) instead of forcing the default — otherwise
  `Tinyc.create(Paths)` (which loads the paths' target, then calls
  `create()`) would throw when the paths' triple differs from the
  device ABI triple.
- `Tinyc.java`: `create(Paths)` now calls
  `TinycNative.ensureLoaded(paths.triple)` before creating the state
  (it does not go through `create()`'s default load);
  `applySysrootIfNeeded()` now registers only directories that exist
  (`sysroot/include` always; `sysroot/include/<triple>` only if
  present — only bionic has that subdir; `sysroot/lib` only if
  present — darwin has no sysroot lib, wasm32 has none). Previously
  it registered all three unconditionally.
- `build.gradle` comment and `TinycInstrumentedTest.java` comment
  updated from `libtinyc.so` to `libtinyc-<target>.so`.
  `TinycJvmTest.java` left alone (its `/data/app/lib/libtinyc.so`
  strings are test inputs to `TinycArgs.forMain`, not tied to the
  real `.so` name).

### Consumer test

New `packages/android/consumer-test/app/src/androidTest/java/com/tinyc/consumertest/TinycCrossTargetTest.java`:
one test method per non-android target (7 methods): x86_64/aarch64/
riscv64-linux-gnu, x86_64-w64-mingw32, arm64/x86_64-apple-darwin,
wasm32-wasi. Each inits that target, compiles a hello that
`#include <stdio.h>` (exercises the staged sysroot) and checks the
output format magic.

Format rules (verified locally against the cross-matrix Linux dists'
tinyc binaries): TCC writes ELF objects for every target
(`ELF_OBJ_ONLY`), so `-c` (OUTPUT_OBJ) cannot tell win32 or darwin
apart from the same-CPU linux-gnu target. So: linux-gnu x3 use
OUTPUT_OBJ + ELF `e_machine` (62/183/243 — linking a hosted exe
needs the target's `libc.so.6`, absent on the device); darwin x2 and
win32 use OUTPUT_EXE + Mach-O magic `cf fa ed fe` / PE `MZ`
(`4d 5a`); wasm32 uses OUTPUT_EXE + `-nostdlib` + `\0asm` magic
(wasm32 `-c` fails with "wasm: object-file output not supported
(single module output only)"; plain wasm32 exe link fails with
"crt1.o not found" because wasm32 has no crt objects — `-nostdlib`
fixes it; wasm32 `-run` is unsupported by design).
`setOptions("-nostdlib")` is used for the wasm32 method.

One target per process: each method runs in its own instrumentation
process, so the module now uses the AndroidX Test Orchestrator
(`consumer-test/app/build.gradle`: `testOptions { execution
'ANDROIDX_TEST_ORCHESTRATOR'}`, `androidTestUtil
'androidx.test:orchestrator:1.5.1'`, `testInstrumentationRunnerArguments
clearPackageData: 'true'`). Without it the methods would share one
process and the second target load would throw
`IllegalStateException`.

### Two pre-existing bugs found and fixed during verification

(both in `packages/android/build.sh`, both in this commit)

1. `jvm-test`'s NDK compile-check was missing `-I../../core`
   (`tinyc_io.h` lives in `core/`, the check only passed `-I`
   vendor + jni) — and the pristine vendor `libtcc.h` lacks the
   `tcc_set_io` / `tcc_get_io` declarations (the patches add them in
   the real kernel tree), so the check also got
   `-Wno-error=implicit-function-declaration` with a comment
   explaining the header mismatch (the real build compiles against
   the patched tree header and keeps them as errors).
2. `manual-aar`'s zip step did `(cd stage && zip -q -r
   <existing-aar> .)` — `zip -r` updates in place and never removes
   entries no longer in the source, so a rebuilt AAR kept stale
   entries; fixed by `rm -f` the output AAR before zipping.

A regression introduced and fixed in the same session: the first
`build_so` edit dropped the `rm -f .../.gitkeep .../PLACEHOLDER.md`
line for `src/main/jniLibs/`; the first manual-aar AAR shipped those
placeholder files. The line was restored after the `.so` loop; the
clean AAR above (0 placeholder entries) is the evidence.
